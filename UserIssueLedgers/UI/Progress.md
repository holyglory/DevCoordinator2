# User Issue Ledger: UI / progress

| ID | Applies to | Mistake pattern | Required behavior | Prevention and verification |
| --- | --- | --- | --- | --- |
| UIL-UI-PROGRESS-001 | Progress delivery charts at hourly, daily, and weekly ranges | A filled polyline made discrete completion counts look like a meaningful area while the label called the values cumulative, so the owner could not tell whether the shape represented work per bucket, a running total, or something else. After replacing the area, the running-total line was painted after the bar-value labels and crossed over their glyphs, hiding numbers at realistic intersections. Missing test and token evidence could also sit on the same visual baseline as a measured zero. | Show discrete completed work as bars and a thin running-total line with an explicit legend. Never fill the area under these lines. Paint the running-total line behind bars and value labels; keep value labels topmost with a solid chart-background halo so every number remains readable at crossings. Keep missing test or token buckets blank and label the unavailable or partial evidence in plain language instead of drawing zero. | Use uneven, zero, partial, entirely missing, and deliberate line/label-crossing fixtures for every range. Verify bar and running-total values against the exact table, assert SVG paint order places running lines before labels, inspect chart titles/tooltips, confirm no filled chart geometry exists, and check the rendered desktop, user-comment, and narrow pages for readable labels, truthful blanks, clipping, and overflow. |
| UIL-UI-PROGRESS-002 | Progress release-work list and task selection | A heuristic based on status, missing estimates, request kind, and approximate size was labelled Priority queue. Imported outcome prose appeared as the task name, inferred impact days looked measured, and the absence of a dependency model was presented as a task fact. Live acceptance then showed that raw unblock and reopening notes can contain internal codes, test names, and implementation detail even when the title is clear. | Present open release work in the same order as the Plan. Lead with the owner-facing task title and show only recorded status, estimate, elaboration request, and a simple Reopened state in the compact summary. Keep raw outcome, impact, unblock, verification, technical note, and event-note prose out of this surface; exact Plan continuation remains the route to full context. Do not claim owner priority, dependency, impact days, or a ranking until those concepts are explicitly modeled and recorded. Selection is local interface state and must not reread or repaint the whole page. | Test nested Plan order, long plain titles, sized and unsized work, technical marker text in every hidden planning field, reopening with and without a note, and elaboration requests. Select every rendered row and verify DOM identity, scroll, focus, API-call count, exact Plan continuation, and the absence of priority, impact-day, dependency, rank, imported-outcome, unblock, and event-note language. |
| UIL-UI-PROGRESS-003 | Progress release forecast and evidence-quality explanation | The page showed a precise-looking date and vague attention language without first explaining which inputs were absent, why confidence was low, or whether missing evidence had been counted as zero. | Pair every available date range with its confidence and a concise Forecast quality explanation naming missing estimates and the missing target date. Call the date provisional. Explain missing test and token evidence in their own aligned lanes so token coverage is not falsely presented as a forecast input. When pace cannot support a date, show an honest unavailable state and its concrete reason. | Exercise available, ready, no-release, insufficient-history, many-unestimated, partial-test, partial-token, and fully unavailable states. Verify every visible claim maps to the response contract, no missing value becomes zero, the forecast never reads as a promise, and the exact counting disclosure explains any approximation. |
| UIL-UI-PROGRESS-004 | Progress completion bars at hourly, daily, and weekly ranges | The delivery charts showed only finished tasks and completed planned lines, so a rising backlog was invisible and completion activity could look like net progress even when just as much new work entered the Plan. | Pair completed work above the chart baseline with newly created tasks and newly added planned lines below it in the same bucket. Keep the running-total line limited to completed work, distinguish incoming bars and labels without implying that estimate reductions or dropped work are new scope, and state the direction explicitly in the legend and accessible chart description. | Use buckets containing completions, creations, initial estimates, estimate increases, estimate reductions, dropped tasks, zeros, and both directions together for every range. Verify API values against permanent Plan events, assert above/below-baseline SVG geometry and paint order, inspect titles and exact-value rows, and check the rendered desktop and narrow pages for readable labels, clipping, overflow, and unambiguous direction. |
| UIL-UI-PROGRESS-005 | Opposing completion and incoming bars within one Progress chart lane | Completed and incoming bars were normalized against separate maxima, so equal values on opposite sides of the baseline rendered at different lengths and visually misrepresented their relative pace. | Use one shared magnitude scale for completed and incoming bars within each lane. Equal values must have equal rendered lengths above and below the baseline, while task counts and planned-line values keep their own independent lane scales. | Use equal-value pairs, completion-dominant buckets, incoming-dominant buckets, zeros, and changing maxima across hour, day, and week ranges. Assert the exact SVG lengths for matching values and proportional lengths for unequal values, then inspect the user-comment width and narrow chart for truthful comparison, readable labels, clipping, and overflow. |
