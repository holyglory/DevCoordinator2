# User Issue Ledger: UI / planning

| ID | Applies to | Mistake pattern | Required behavior | Prevention and verification |
| --- | --- | --- | --- | --- |
| UIL-UI-PLANNING-001 | Plan destinations, hierarchical task rows, and Gantt interactions at wide and narrow viewports | The Plan page compressed long task descriptions, row actions, hierarchy, and the graphic timeline into one cramped grid, so the timeline became mostly empty space and the task collection was difficult to scan. | Keep the named plan and task collection immediately recognizable, separate a concise hierarchical task navigator from a dominant timeline canvas, and reveal details contextually. The chart must provide truthful horizontal scrolling, pan, zoom, hover details, selection, drag-and-drop, resizing, and an accessible non-pointer path without displacing primary content. | Compare the approved visual target with a rendered 1440×1024 capture; verify representative narrow behavior, long-content and dense-task fixtures, navigator/timeline synchronization, every enabled chart control, drag cancellation and failures, resize persistence and reload, keyboard alternatives, contrast, clipping, overlap, and document overflow. |
| UIL-UI-PLANNING-002 | Plan sizing and chart coverage | Unsized leaf work advanced the cumulative cursor by zero and therefore vanished from the graphic; verification-heavy work also had no honest way to express that execution, investigation, and reruns consume substantial effort even when little code is written. | Render every active task. Keep measured lines proportional, place missing estimates in an explicitly non-proportional “Not estimated” band, and let an owner add the missing estimate without inventing a number. Do not silently equate elapsed testing time with lines of code. | Use a fixture containing sized leaves, unsized leaves, unsized-only parents, and mixed parents. Verify every row has a reachable chart mark, the numeric axis excludes unknown work, the non-proportional band is labelled, and estimate entry persists through the real API. |
| UIL-UI-PLANNING-003 | Owner-facing task language | Imported and agent-created task names exposed release codes, database/provider names, abbreviations, and verification jargon, forcing the owner to translate the ledger before understanding what users gain or what remains unsafe. The problem recurred in another repository after one plan was manually rewritten, and a one-time rewrite did not give the owner a durable way to ask the responsible agent for clarification. | Task names shown to the owner must use short everyday language that says what a person can do or what will be checked. Put release codes, provider names, test classes, implementation terms, and evidence identifiers in technical notes, not the visible title. Every task must let an administrator persist an `elaboration needed` request. Standard planning and task responses must surface every outstanding request prominently enough that an agent cannot lose it to task truncation. The request stays open until an agent atomically saves genuinely changed owner-facing wording and clears it; clearing the mark alone is rejected. Do not imply an automatic generator exists. | Before handoff, review every visible task title in the affected plan for unexplained abbreviations and implementation nouns. Exercise the request on planned, in-progress, done, parent, leaf, sized, and unsized tasks; verify authorization, append-only requested/completed events, reload persistence, failure recovery, and wide/narrow rendering. Verify `plan.overview`, task reads, and task mutations expose outstanding requests even when finished tasks are truncated; verify a clear-only update fails while a wording-change-and-clear update succeeds and remains understandable without engineering knowledge. |
| UIL-UI-PLANNING-004 | Plan selection and tree disclosure | Selecting a task or opening and closing its children called the complete route renderer, aborted and re-fetched the plan, and replaced the whole page, causing a visible blink and avoidable loss of visual continuity. | Selection, task disclosure, navigator disclosure, and detail-tray disclosure are local interface state. Update only the affected row, bar, descendants, minimap mark, and detail tray; preserve scroll and focus without a network read or whole-page replacement. | Instrument plan-overview calls and DOM identity. Select tasks and repeatedly expand/collapse parents at wide and narrow sizes; verify no additional plan read, the workspace node remains the same object, scroll positions stay stable, focus moves only as intended, and no loading skeleton or page flash appears. |
