# User Issue Ledger: Agent workflow

| ID | Applies to | Mistake pattern | Required behavior | Prevention and verification |
| --- | --- | --- | --- | --- |
| UIL-AGENT-WORKFLOW-023 | User-reported bugs and follow-up corrections | The agent delivered a supporting cache while the reported behavior still failed, then answered repeated reports with apologies and diagnoses instead of continuing repair. | Treat bug reports as repair requests unless explicitly limited to explanation or investigation. Preserve the original visible acceptance criterion through subtasks, fix necessary in-scope dependencies, and do not stop while safe repair work remains. Preserve real approval boundaries and report genuine blockers precisely. | Enforce the universal repair mandate with must-catch policy mutations for diagnosis-only stopping, repeated fix instructions, subtask substitution and unverified closure; retain explanation-only and genuine-blocker exceptions. Require real data on the originally reported surface before closure. |
| UIL-AGENT-WORKFLOW-001 | Planning and implementation in every repository | Reusable user-indicated mistakes were handled only in the current task and could recur in later work. | Preserve each confirmed pattern in its narrowly scoped project ledger and apply every relevant row before implementation. | Enforce the universal policy contract, realistic policy-checker fixtures, and recursive scoped-ledger validation. |
| UIL-AGENT-WORKFLOW-002 | Designing or extending user-issue ledgers | Unrelated UI, business, automation, or coding corrections were combined in one broad ledger, obscuring which rules applied. | Keep one path-bound ledger per surface or bounded business perspective; never revive a single catch-all file. | Bind every ledger path to its title and ID namespace, and test rejection of a mixed-scope file plus acceptance of multiple nested business perspectives. |
| UIL-AGENT-WORKFLOW-004 | Full test, debug, audit, migration-rehearsal, and deployment cycles | Agents stopped at each non-critical gap, fixed it, and restarted the full cycle, losing later failure evidence and repeating expensive setup. | Finish the current cycle after non-critical failures, record all actionable gaps concisely, batch related fixes after the pass, and then rerun the complete relevant cycle. Stop early only when continuation risks harm, corrupts shared state, destroys evidence, or makes later results invalid. | Add policy and checker fixtures for finish-pass-then-batch-fix behavior; make multi-check runners and ad-hoc independent diagnostic command groups collect every exit status instead of short-circuiting with fail-fast chaining; verify a usable test deployment may proceed with disclosed gaps while readiness remains incomplete. |
| UIL-AGENT-WORKFLOW-005 | Engineering scope and risk controls | Agents either reduced an explicit commitment for speed or silently added unrequested recovery, preservation, encryption, migration, hardening, publication infrastructure, or other behavior. The policy later called implementation gaps more punishable than reasonable over-engineering, biasing agents toward treating tentative language and illustrative details as commitments. In the repository consolidation, the agent designed an atomic multi-release system after the owner had asked for one live checkout and ordinary worktrees; earlier prevention also turned merely noticing an optional idea or routinely invoking a reviewed tool into an exhaustive interview. | Implement the complete explicitly agreed result without broadening it or trading completeness for speed. Treat “ideally,” “for example,” “something like,” “could,” and illustrative formats as direction unless the user selects them or they are necessary for the requested behavior. Add reliability, security, recovery, migration, preservation, compatibility, UI, or infrastructure work only when acceptance criteria, confirmed assumptions, current-system evidence, or the minimum end-to-end implementation requires it. If a focused request grows beyond three product subsystems, needs a new platform abstraction, or approaches 1,000 changed lines, pause once to explain the actual scope and recommend the smallest sufficient architecture. More checks, parsers, adapters, or formats do not by themselves make an implementation complete. Before implementing any addition outside the evidence-backed boundary, obtain explicit approval; do not interrupt merely to mention an optional idea that will not be implemented. | Require the exact-scope/completeness distinction, tentative-language boundary, evidence-backed supporting-work boundary, large-scope pause, smallest-sufficient-architecture recommendation, approval-before-addition rule, proportional questions, and no-action/routine-use guards in universal policy. Add must-catch fixtures for omitted explicit work, mandatory illustrative details, automatic supporting systems, hidden large scope, completeness measured by extra machinery, unrequested release/publication machinery, and hypothetical edge cases; preserve passing fixtures for selected details, necessary end-to-end support, ordinary low-level choices, and declined optional ideas. |
| UIL-AGENT-WORKFLOW-006 | Agent-controlled context, tool selection, and tool output | Agents repeatedly loaded broad unchanged rules, unrelated skills or tools, oversized file ranges, raw logs, full audit reports, or unchanged images, causing high token use without improving the result. | Load only context and capabilities relevant to the current task, use targeted reads and bounded software-generated receipts, keep complete raw evidence and audit results in cold artifacts, and do not reload unchanged content already available in the live context. Every artifact receipt must identify at least the saved filename. | Measure canonical policy size and startup catalogs, add policy checks for relevance and bounded output, require filename-bearing artifact receipts, and distinguish host-injected overhead from repository-controlled behavior. |
| UIL-AGENT-WORKFLOW-007 | Workflows that use isolated workers across multiple agent runtimes | Shared workflows exposed one runtime's effort labels and worker controls, making portable skills depend on private interface names. | State the semantic requirement in shared contracts: fresh isolated worker context, complete prompt delivery, bounded artifact receipts, and runtime/user-selected effort unless the workflow has a separately confirmed effort requirement. Put any unavoidable runtime mapping in its installation or provider adapter, never in the shared skill or generated prompt. | Scan shared skills, policy, metadata prompts, and generated prompts for runtime names or private controls; require neutral isolation wording and complete prompts. Preserve passing adapter fixtures for factual installation paths and provider-specific metadata. |
| UIL-AGENT-WORKFLOW-008 | Heavy repository-audit skill activation | Full-repository implementation, test-coverage, and implemented-UI audits could enter context through broad implicit matching even when the user had not deliberately requested their expensive exhaustive workflows. | `full-repo-audit`, `full-repo-test-coverage-audit`, and `ui-implementation-audit` require deliberate direct invocation through the active runtime's native skill mechanism; ordinary implementation, UI work, review, testing, visual checking, or gap-finding requests must not activate them implicitly. | Keep each provider adapter's implicit-invocation gate disabled, state the runtime-neutral explicit-only rule in every shared skill contract, and validate realistic deliberate-invocation and ordinary-work prompts without embedding provider command syntax in shared text. |
| UIL-AGENT-WORKFLOW-009 | Deterministic audit and verifier CLIs | Context isolation depended on the agent remembering an optional quiet/receipt flag, so a valid invocation could still print a complete audit report into model context. | Software owns artifact creation and context-safe output: a normal agent-facing verifier invocation writes complete results to deterministic files and emits only a bounded receipt naming those files; printing a full report requires an explicit human-only opt-in. | Exercise clean, finding, coverage-failure, and setup-failure paths; prove artifacts contain full evidence, default stdout is one bounded receipt, and only the explicit human-output flag prints the report. |
| UIL-AGENT-WORKFLOW-011 | `user-journey-docs-audit` activation | A greenfield request to critique a domain idea, discuss requirements, and write a specification was treated as a request to audit an existing documentation set because both tasks mentioned product intent, UI, and pre-implementation decisions. | Invoke the skill only when existing product or journey documentation is the audit target and the user requests a documentation-completeness or UI-readiness assessment. Do not activate it for brainstorming, domain or data modeling, database/system specification, ordinary requirements discussion, or co-writing a new specification; “do not start coding,” “critique,” and “roast” are not audit signals by themselves. | Put the complete positive and negative trigger boundary in selector-visible frontmatter, stop before inventory or interview when the applicability gate fails, mirror the boundary in user-facing metadata and README guidance, and test realistic must-call and must-not-call prompts including the reported numbering-system request. |
| UIL-AGENT-WORKFLOW-012 | In-scope local preview, browser QA, and development-runtime coordination in any repository | Agents repeatedly asked for explicit chat authorization before using Playwright or the configured DevCoordinator even though the user wanted those routine tools used autonomously, delaying implementation and verification. | Treat the user's instruction as standing permission to invoke browser automation directly and use the configured development coordinator for in-scope local runtime work in any repository without a separate chat approval. The permission does not expand scope or authorize destructive, production, credential, trust-bypass, or otherwise separately gated actions. | Require the standing-permission boundary in universal policy; reject direct permission questions, stated approval needs, target-first prompts, and ask-before-use phrasing for both tool families; preserve false-positive guards for material scope expansion, production mutation, destructive work, credentials, security gates, installation, and host-owned approval prompts. |
| UIL-AGENT-WORKFLOW-014 | Completion-ledger entries and incomplete-work handoffs | Completion ledgers contained implementation jargon, identifiers, and low-level plumbing descriptions without first saying what users can or cannot do, why the gap matters, or where development is going. The stored state was technically populated but unreadable as a progress view. | Write every database-ledger field for a non-specialist reader first: name the incomplete outcome in plain language, state the present user or product impact and whether it blocks readiness, describe the next result or unblock condition, and explain the observable proof that will close it. Technical detail, affected paths, identifiers, and test names may follow that explanation but never replace it; raw logs stay in cold artifacts. When reporting progress, summarize the ledger's direction, current capabilities, and blockers in the same plain language. | Require a reader-first software-owned database-ledger contract in universal policy and repository guidance. Add semantic policy fixtures that reject technical-only explanations, implementation identifiers as substitutes for user impact, or any Markdown ledger fallback and accept concise plain-language database records followed by useful technical detail. Review request-related active database records and handoffs against the contract before readiness. |
| UIL-AGENT-WORKFLOW-015 | Approval requests and other blocking questions | Agents repeatedly interrupted the user with piecemeal approval requests framed around implementation jargon, internal identifiers, digests, commands, or prescribed confirmation phrases. They also treated already requested, authorized administrator actions and append-only decision summarization as new approval decisions. | Before any genuinely blocking question, finish available read-only investigation and bundle all known consequential effects into one plain-language decision. Explain the problem, recommended outcome, boundaries, user-visible or operational consequences, and meaningful tradeoffs before optional technical detail. Approval applies to that recorded outcome and its boundaries, not merely to implementation details named in the message. A plain “yes” is sufficient; never make the user repeat or transcribe an internal identifier, digest, command, or technical incantation. Use a mandatory host or tool approval control directly rather than relaying its internals through chat. Ask again only when later evidence materially changes the approved outcome or boundaries. Do not ask again for an in-scope administrator write the user requested and the product authorizes, or for append-only decision summarization. | Require this approval contract in universal policy and its semantic checker. Add must-catch fixtures for technical-only questions, approval before read-only discovery, serial approvals as implementation details appear, approval limited to named mechanics, rejection of a plain yes, identifier repetition, redundant administrator confirmation, and summarization approval. Preserve false-positive guards for one bundled plain-language decision, a directly invoked native approval control, immediate authorized administration, direct summarization, and a later materially changed plan presented as one new decision. |
| UIL-AGENT-WORKFLOW-016 | `ui-implementation-audit` worker dispatch | The UI audit hard-coded one runtime's low-effort and context-fork controls for every source and visual worker, coupling correctness to private adapter settings and preventing the runtime or user from selecting appropriate capability. | Keep each UI-audit worker in a fresh isolated context with the complete bounded prompt and artifact-first receipt, but do not prescribe, validate, or record a required reasoning-effort level or provider-specific worker control. Use the runtime/user-selected worker defaults. Manual fallback remains available when workers cannot be spawned. | Remove effort requirements and private worker-control names from active contracts, prompts, execution ledger, metadata, and README. Retain complete prompt delivery, bounded filename-bearing receipts, worker status/provenance, and manual-fallback tests. Reject reintroduction of an effort requirement, equality gate, inherited lead context, or runtime-branded shared instruction. |
| UIL-AGENT-WORKFLOW-017 | Requests to inspect, explain, summarize, or elaborate completion-ledger work | An agent treated a read-only request to elaborate tasks in chat as permission to rewrite the parent task and create child tasks in the ledger. | Read the ledger and answer in chat. Do not create, update, split, reorder, start, close, or otherwise mutate ledger work unless the user explicitly requests a ledger change; wording such as “before execution” reinforces that no work should begin. | Classify the request as answer/explain versus change before invoking any ledger mutation. Add must-catch coverage for “check the ledger and elaborate the tasks” and equivalent read-only wording, with passing cases for explicit requests to edit, split, reprioritize, or update the ledger. |
| UIL-AGENT-WORKFLOW-018 | Parallel work and long-running diagnostic cycles | Agents proposed repository-local fixed worker budgets, then waited for the full test rig to finish before starting work on its first ordinary failure. | Submit every dependency-safe, non-conflicting leaf to DevCoordinator2 immediately and let its measured host-wide adaptive scheduler control admission; do not add repository-local worker counts, fake dependency chains, or a second capacity controller. When the first ordinary failure appears, begin diagnosis and fixing immediately in isolated state while the original sealed run continues unchanged and gathers the remaining failures. | Require app-wide policy and semantic fixtures for central adaptive admission, ready-work scheduling, all-settled siblings, dependency/shared-state serialization, first-failure concurrent diagnosis and fixing, sealed-run isolation, event-driven waits, and the 100 ms interval ceiling. Reject repository-local budgets, fixed worker counts, sibling cancellation, waiting for run completion before beginning fixes, and mutation of the running evidence surface. |
| UIL-AGENT-WORKFLOW-019 | Parallel decomposition and implementation delegation | Agents delegated implementation before shared schemas, directory layouts, ownership boundaries, or a cross-component acceptance example were settled. Workers then made incompatible interface choices, edited the same files, recursively spawned more implementers, and competed to integrate the result. | Delegate implementation only after shared contracts and one cross-component acceptance fixture are fixed. A branch is independently ready only when no shared-interface decision or mutable-file ownership remains unresolved. Use at most two implementation agents plus one integrator for a tightly coupled subsystem; a subagent may spawn another implementer only when the parent explicitly authorizes that specific independent branch. The parent remains the sole integration owner. This ownership bound does not cap genuinely independent checks or the host-wide execution scheduler. | Require a distinct contract-readiness section and semantic fixtures that reject premature delegation, unresolved shared interfaces, overlapping mutable files, oversized tightly coupled teams, unauthorized nested implementation delegation, and multiple integration owners. Preserve passing fixtures for independent branches, explicitly authorized nested work, parent-owned integration, and unrestricted coordinator admission of dependency-ready checks. |
| UIL-AGENT-WORKFLOW-020 | Validation cadence during implementation, integration, and release | Agents ran the complete suite after individual plan items, file edits, commits, and delegated results; multiple workers duplicated complete runs, test-plumbing changes repeatedly restarted release proof before either the implementation or harness was frozen, and small interface fixes were withheld from owner inspection until the full rig finished. This spent substantial time validating transient states, delayed useful feedback, and encouraged stop-fix-restart cycles. | During implementation, run cheap checks and focused tests that can invalidate the current design or changed behavior, then complete a coherent batch before broader validation. When an authorized non-production interface surface exists, publish the focused passing result for preliminary owner inspection before broad validation and keep that surface available while the broader run proceeds against a frozen snapshot. Run pre-merge validation after shared interfaces and integrations stabilize, and one fresh complete release pass over the frozen candidate. A failed complete pass remains sealed and finishes collecting every safe finding while isolated repair may begin; reconcile and batch the fixes, use focused checks during repair, then run one final complete pass. One agent owns complete-suite execution. Delegated agents run only focused checks unless explicitly assigned the sealed integration pass. Test-plumbing-only changes do not trigger another complete release pass until implementation and test infrastructure are both frozen. | Require semantic-checkpoint and preview-first policy sections with fixtures that reject complete runs after every small step, withholding an authorized focused preview behind the complete suite, broad validation before a coherent batch or stable interfaces, multiple suite owners, unassigned delegated suite runs, and plumbing-only release reruns. Preserve passing fixtures for cheap invalidating checks, immediate preliminary preview after focused proof, continued owner feedback beside a frozen broad run, one assigned integration owner, first-failure isolated repair beside the unchanged sealed pass, one final batch rerun, and a fresh frozen-candidate release pass. |
| UIL-AGENT-WORKFLOW-021 | Universal policy, repository policy, and independently maintained integrations | Agents mixed one repository's test-server assumptions into universal guidance and described independently maintained systems as if either depended on or knew about the other. | Keep universal policy repository-, product-, and runtime-neutral. Put concrete test environments, ports, shared-worktree assumptions, and product names only in the owning repository's local instructions. Independently maintained systems expose neutral interfaces and remain usable without one another; any optional connection belongs in configuration or an adapter rather than either system's core contract. | Review global and local policy as separate scopes; reject project names and project-only topology in universal additions, reject foreign-product dependencies in either independent core contract, and accept a concise local declaration that activates neutral global behavior for its own environment. |
| UIL-AGENT-WORKFLOW-022 | Tool selection and multi-call orchestration | Agents issued safe independent reads sequentially and used repeated model turns for mechanical pagination, filtering, joins, deduplication, and aggregation, increasing latency and context cost. | Before tool use, partition calls into dependency layers; execute each safe independent layer concurrently, use bounded programmatic orchestration for mechanical read-only workflows, and serialize only semantic decisions, approvals, true data dependencies, or conflicting mutations. | Require compact structured conclusions, evidence, and errors; exercise independent reads, dependent calls, paginated aggregation, all-settled failures, and conflicting writes so policy rejects needless serialization and unsafe parallel mutation. |
