| UIL-DATA-USAGE-ANALYTICS-004 | Collector schema compatibility for Progress and Codex Usage | An additive collector migration advanced the schema version while leaving the measured-token contract unchanged; the reader rejected every configured source and blanked real usage. | Review the canonical migration before accepting a new schema, explicitly support verified compatible versions, and continue rejecting unreviewed versions and taxonomy changes. Never substitute context-token estimates for provider measurements. | Exercise schema 4 and the schema 5 added context table and execution columns with identical provider totals, privacy exclusions, and missing buckets; retain a future-schema rejection test and verify the affected live Progress route after publication. |
| UIL-DATA-USAGE-ANALYTICS-001 | Codex provider-token categorization and DevCoordinator2 repository usage charts | The agent proved an ideal fixture where a classified model operation owned the provider token row, then treated classified tool/model counts as evidence that real token totals would also be categorized; in live multi-agent work the token-bearing delegated or next-turn operations remained `unknown` while classified operations carried no token rows | Keep `unknown` visible whenever the canonical token-bearing operation is unclassified, never move tokens to a nearby activity by guesswork, and do not claim activity categorization works until declarations survive the actual delegated-thread and turn boundaries that emit provider usage | Test same-turn, next-turn, parent/delegated-thread, tokenless-classified-operation, and token-bearing-unknown-operation cases in the canonical collector and the downstream aggregate; prove provider `total_tokens` remains invariant, classified shares come only from the owning operation, partial coverage remains explicit, and a real repository report no longer collapses to 100% unknown when declarations were made |
| UIL-DATA-USAGE-ANALYTICS-002 | Codex Usage repository collection aggregation | The collection repeated broad source scans once per repository; production-sized reads hit the two-second query deadline and those timeouts were flattened into unavailable rows, so both the latency and apparent data state were artifacts of the reader | Bound source work independently of repository count, query only operations attributed to the requested repository/window, and preserve the difference between mapping pending, no measurements, unsupported schema, and an actual unavailable source without inventing zeroes | Use production-scale schema-4 fixtures with unrelated historical rows and multiple repositories/sources; prove targeted query plans and results, a complete 11-row collection response below one second on repeated and cold-path checks, invariant totals/categories, and exact unavailable-reason composition |
| UIL-DATA-USAGE-ANALYTICS-003 | Repository-detail usage series consumed by Progress and Codex Usage | The compact collection was optimized, but repository-detail token and coverage reads still scanned broad production tables. The largest source could hit its deadline and disappear while smaller incomplete sources survived, causing Progress to report partial zeroes despite real project measurements. | Resolve one repository's exact attributed operations first, then read their model-request, tool-invocation, and coverage records through indexed identifiers within the requested time window. Preserve explicit per-bucket evidence presence so failure-only partial coverage cannot manufacture a zero, while a real provider-reported zero remains measurable. | Use a production-scale fixture with large unrelated token and coverage history, real project tokens, a true zero observation, and an unavailable sibling source. Assert indexed query shapes, bounded completion, exact totals and phase buckets, null failure-only gaps, retained real zeroes, unchanged privacy fields, and matching Progress/Codex Usage results. |
